# Реальные проверки Claude Code CLI

Срез: 2026-11-02. Живые приёмочные запуски ниже работали на **Claude Code 2.1.316**; версия записана самим CLI в `system/init.claude_code_version`. Во время работы CLI обновился с ранее исследованной 2.1.296, поэтому результаты привязаны именно к версии из runtime receipt.

Все тесты использовали настоящий Claude CLI, локальный Messages-шлюз и NeuralDeep. Конфигурация строилась через `build_settings`, без импорта пользовательских плагинов и глобальных MCP. Включены все 14 MCP-серверов NeuralDeep; `--strict-mcp-config` исключал посторонние MCP вроде запускаемого через npx Playwright. Во всех перечисленных init 14 серверов показали `connected`. Это подтверждение подключения, а функциональные проверки отдельных сервисов находятся в отдельном отчёте.

## Автоматическое сжатие: PASS

Модель: `qwen3.8-27b~xhigh`, подписка. Настоящая четырёхходовая сессия `--input-format stream-json` прошла с exit 0 за 286.071 секунды. Пользовательская команда `/compact` не отправлялась.

CLI выдал настоящий `system/compact_boundary` с `compact_metadata.trigger: auto`:

- `pre_tokens`: 38 711;
- `post_tokens`: 5 086;
- `cumulative_dropped_tokens`: 33 625;
- длительность самой compaction: 126 517 мс.

Эти числа — метаданные сжатой истории Claude. Полные следующие запросы сохраняют системные сообщения и схемы MCP: фактический `usage.input_tokens` снизился с 38 671 перед сжатием до 31 371 после него; следующий ход — 31 408. Нельзя интерпретировать 5 086 как полный размер следующего API-запроса.

Все четыре ответа правильны: FIRST_OK, SECOND_OK, THIRD_OK, затем требуемая капсула ND-41-73, сохранённая через сжатие. Это доказывает автоматический запуск, завершение и продолжение разговора с сохранением проверяемого факта.

Receipt: `.local/cli-validation/20261102T154311376875Z/compact/receipt.json`; события и debug рядом.

**Параметры только smoke:** окно 100 000 и `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=40`. Они записаны исключительно в settings конкретного процесса проверки. Основная конфигурация пользователя не менялась. Уменьшенный порог нужен, чтобы воспроизводимо проверить сжатие без заполнения полного 262k-контекста.

Предыдущие двухходовые попытки сохранены: CLI достигал порога, но сообщал `Reactive compact: no assistant messages in summarize set, bailing`, поскольку в защищённой недавней истории ещё не было подходящих старых assistant-сообщений. Это не принято за успешное сжатие. Первая проба с 1% также не принята: порог оказался ниже обязательного системного/MCP-префикса. После достаточной истории четырёхходовая проверка дала настоящий compact boundary.

## Встроенный Workflow: PASS

Модель: `qwen3.8-27b~xhigh`, подписка. CLI действительно вызвал **встроенный Workflow**, исполнив предоставленный inline JavaScript с `export const meta`, `phase`, `parallel` и двумя вызовами `agent`.

Авторитетный журнал самого workflow содержит два `started` перед первым `result`, затем правильные FLOW_B=667 и FLOW_A=323. Получено `task_notification.status=completed`. После первоначального промежуточного сообщения CLI обработал завершение и выдал финальный ответ с обоими результатами. Процесс завершился exit 0 за 196.343 секунды.

Receipt: `.local/cli-validation/20261102T153745009903Z/workflow/receipt.json`. Копия реального журнала: `workflow-journals.json` в той же папке; оригинальный абсолютный путь сохранён внутри. Это проверка нативного Workflow, не MCP-замена и не только наличие инструмента в списке.

## Отдельные Task/Agent: PASS на Sonnet, ограниченная устойчивость Qwen

В запуске `.local/cli-validation/20261102T153040630816Z/parallel` два настоящих асинхронных дочерних агента выполнили Bash-инструмент с отдельными вычислениями 17×19=323 и 23×29=667. Помощник записывал время начала и завершения каждого процесса вокруг трёхсекундной паузы. Реальное перекрытие исполнения — **2.9943 секунды**. Оба агента сообщили completed.

Этот запуск не принят как полный цикл: основной агент не успел выдать финальный результат за первоначальное диагностическое окно 180 секунд. Повтор с точными командами в Task prompts получил 600 секунд, но не вернул даже первого содержательного ответа модели; исходный таймаут сохранён в `.local/cli-validation/20261102T153639688913Z/parallel/receipt.json`.

Таким образом, непосредственное параллельное исполнение дочерних агентов измерено; полный успешный цикл параллельных агентов с финалом основного агента доказан в отдельном встроенном Workflow. Утверждение, что каждый Task/Agent-запуск на каждой модели надёжен, этими данными не подтверждается. Прямая Task/Agent-проба на `claude-sonnet-5.5` по кошельку **прошла полностью с обычными builtin-плагинами и hooks**: exit 0 за 413.154 секунды, оба дочерних агента вернули 323 и 667, фактическое перекрытие Bash-исполнения — **2.9999 секунды**. Финальный ответ основного агента содержит оба правильных значения. Нативный `result.subagent_stats`: spawned 2, completed 2, failed 0; глубина 1. Два вызова относятся к одному id assistant-сообщения, хотя SDK выводит каждый блок отдельным событием.

Receipt: `.local/cli-validation/20261102T154802199451Z/parallel/receipt.json`. В нём сохранены фактический финал и статистика. Дополнительная диагностика с отключёнными только в smoke hooks выполнялась отдельно: два дочерних процесса также перекрывались на 2.9978 секунды, но до финального ответа основного агента запуск остановлен после 234 секунд, чтобы завершить обновление собственного шлюза. Receipt `.local/cli-validation/20261102T155302418464Z/parallel/receipt.json` оставлен неуспешным. В его debug зарегистрирован настоящий upstream HTTP 504 и повтор SDK; это не доказательство причины всех ожиданий. Отключение hooks не требуется для уже успешного normal-hook Sonnet результата и не меняет основную конфигурацию.

## Финальный профиль и бюджет 128k: PASS по реальному запросу

После окончательного перезапуска шлюза выполнена ещё одна настоящая короткая проверка default `qwen3.8-27b~xhigh`, обычным CLI без `--bare`, с чистой минимальной конфигурацией и всеми 14 NeuralDeep MCP. Ответ — точное OK, exit 0 за 22.201 секунды. Версия — 2.1.316; ревизия работающего шлюза совпала с текущими исходниками.

Отправленный запрос действительно содержал **`max_tokens: 128000`**: запись `request` в `.local/gateway-events.jsonl`, id `ab2c51e992b647eab363a82f6860b6d5`, 88 инструментов. Последующие `message_delta` и `finished` связаны тем же id; фактический usage 29874 входных / 25 выходных токенов точно совпал с CLI receipt.

Первоначальный диагностический assertion ожидал 128000 в `result.modelUsage.maxOutputTokens` и получил 32000. Исходный receipt с неуспешным assertion **не переписан**. Проверка исходников установленного CLI показала, что это поле отражает статический default модели, а не действующий request override; фактический wire-бюджет проверяется отдельно. Исправленное доказательство с источником и привязкой: `.local/cli-validation/20261102T160757677418Z/default-128k/acceptance-wire-proof.json`.

Отдельный финальный запуск обычного основного `claude` также завершился exit 0 за 22.469 секунды с MAIN_OK. Его запись `request` id `44bc1b8902bf425aa8a34078493cdee8` содержит **230 инструментов и `max_tokens: 128000`**, usage 88578/28. Сводка: `.local/cli-main-profile-final-summary.json`. Эта проверка использовала основной установленный профиль с пользовательскими плагинами/MCP, включая Playwright; она отделена от минимальных диагностических settings.

Принятие 128k выходного бюджета и правильный короткий ответ не означают, что здесь реально сгенерированы 128000 токенов или доказан полный предельный выход на любой модели.

## Граница применимости

Это клиентские функциональные проверки поверх удалённого сервиса NeuralDeep. GPU/железо внешних поставщиков не измерялось и не было условием этих проверок; результаты нельзя использовать как сравнение производительности оборудования или модели обучения. Проверены конкретные модели, billing-режимы, версия CLI и настройки из receipts. Это не общая гарантия каждого workflow на всех моделях.

## Воспроизведение

Переносимый скрипт `scripts/probe-claude.py` по умолчанию только выводит план:

```bash
python scripts/probe-claude.py --test all
python scripts/probe-claude.py --test compact --execute
python scripts/probe-claude.py --test workflow --execute
python scripts/probe-claude.py --test parallel --model claude-sonnet-5.5 --execute
```

С `--execute` выполняются настоящие модельные запросы, а кошелёк тарифицируется. Каждый запуск пишет отдельную папку `.local/cli-validation/`. Порог compaction меняется только в smoke-процессе. Таймаут по умолчанию — 600 секунд; принудительно завершается только собственная группа процессов конкретной диагностики. Пользовательские процессы не завершаются. Успех требует receipt с проверенным результатом, а не только запуска процесса или показа статуса.

В завершённых здесь проверках CLI использовал тогдашний native default `maxOutputTokens=32000`. Позднее основной установщик поднял выходной бюджет до опубликованного предела с учётом штатного потолка клиента 128000; эти receipts не следует переименовывать в проверки полного выхода 128k. Математика резервирования compaction использовала effectiveWindow80000, что подтверждено debug.

Указанные пробы не доказывают качество любых длинных coding-задач, предельный контекст каждой модели, точность token-count оценки или доступность Claude Desktop/Design. Эти свойства требуют отдельных проверок.
