Checked on 2026-11-02. These are compatibility findings, not claims that an end-to-end NeuralDeep integration passed.

**Runtime update:** the direct-name Desktop filter problem below was resolved with truthful labels and opaque Anthropic-format gateway routes, without assigning Claude behavior to non-Claude models. That later run enforced the user's no-Anthropic network requirement inside a verified kernel network namespace; the earlier timeout is preserved as historical evidence. ## Local versions and routing

- CLI: `~/.local/bin/claude`, resolving to `~/.local/share/claude/versions/2.1.296`; `claude --version` reported 2.1.296.
- Desktop Debian package: 4.4212.0. Real executable: `/usr/lib/claude-desktop/claude-desktop`.
- The existing `~/.local/bin/claude-desktop` is a custom shell wrapper. It reads proxy configuration from `~/.claude/settings.json`, starts `claude-proxy-relay.service`, and passes Chromium a proxy-server flag pointing at loopback port 20171. Merely unsetting proxy environment variables does not undo this wrapper's explicit flag. A dedicated launcher should call the real executable directly and set its own environment.
- No credentials were printed or copied during this audit. Existing configuration files were inspected only for field names and selected nonsecret version fields.

## Officially supported gateway contract

Claude Code uses Anthropic Messages on an `ANTHROPIC_BASE_URL` gateway. The local adapter must implement `/v1/messages`, including ordered streaming events, tool blocks and complete termination events. Token counting at `/v1/messages/count_tokens` is optional; without it, the client estimates. Keep-alives matter during long reasoning gaps. Headers, errors, and capability fields require careful handling; the current client sends more than basic chat completion fields. The official documentation explicitly does not support non-Claude upstream models. Such an adapter is our implementation and needs behavioral tests per upstream model. [Gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol), [gateway overview](https://code.claude.com/docs/en/llm-gateway).

Do not turn off all experimental betas indiscriminately: that removes some context-management, schema, structured-output and deferred-tool features. Unsupported upstream fields should be translated deliberately, and unsupported functionality reported honestly. CLI 2.1.296 predates several recovery improvements described by the live documentation, including context-management rejection recovery at 2.1.304 and deferred-tool recovery at 2.1.305. [Gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol).

## Model picker and effort

`modelPicker` is a user/managed/`--settings` setting; repository project and local settings cannot relabel this picker. Its object has `options` and optional `replaceBuiltInOptions`; rows accept `model`, `label`, `description`, and optional `behavesAs`. Thus every NeuralDeep text model and billing variant can have a row and a visible wallet label without patching Claude. `behavesAs` imports a known Claude model's client behavior; it does not declare arbitrary capabilities or numeric limits. Assigning it to a non-Claude model risks making false assumptions. [Settings reference](https://code.claude.com/docs/en/settings-reference#modelpicker).

Gateway discovery is optional and reads only `id`, `display_name`, `description`; it filters IDs to ones containing `claude` or `anthropic`. Raw Qwen/DeepSeek IDs therefore need explicit picker rows. Discovery alone cannot supply context or capabilities. [Connect a gateway](https://code.claude.com/docs/en/llm-gateway-connect#add-gateway-models-to-the-model-picker).

Installed CLI help exposes effort levels `low`, `medium`, `high`, `xhigh`, `max`. Native per-model saved effort is in `modelSettings`; `max` chosen interactively is session-only. NeuralDeep may support a different vocabulary, which must be mapped explicitly or offered as named model variants. The companion `ANTHROPIC_DEFAULT_*_MODEL_SUPPORTED_CAPABILITIES` environment variables do **not** take effect behind a plain `ANTHROPIC_BASE_URL` gateway; they are for provider modes. No amount of adding these variables makes a gateway model advertise arbitrary native effort controls. [Model configuration](https://code.claude.com/docs/en/model-config), [gateway protocol](https://code.claude.com/docs/en/llm-gateway-protocol).

## Context and compaction limits

There is no documented per-row numeric context field. `modelOverrides` maps a known Claude version to a provider ID and imports that known model's assumptions. `CLAUDE_CODE_MAX_CONTEXT_TOKENS` supplies a global context size for eligible unknown custom IDs. In installed 2.1.296, a recognized model, including one recognized through `behavesAs`, bypasses that unknown-model override. A per-model `autoCompactWindow` changes the compaction boundary rather than the reported actual model capacity. Its accepted numeric range is 100000–1000000; arbitrary integers inside the range, such as 131072 and 262144, are representable. A 46K model cannot use that per-model setting. [Model configuration](https://code.claude.com/docs/en/model-config#correct-the-window-for-a-gateway-or-custom-model-id).

These constraints mean that an unmodified stock picker cannot promise exact arbitrary context capacities and proactive automatic compaction across every model switch in a single session. A launch profile can set the true context for its selected unknown model. Switching to a different context class requires restarting under that profile, or accepting and testing an explicitly documented recovery path. Server overlength errors can trigger client recovery only when their wording is recognized. Neither a catalog JSON field nor a fabricated 1M suffix proves safe 46K operation. [Model configuration](https://code.claude.com/docs/en/model-config#context-window-and-auto-compaction).

Read-only inspection of the installed executable also found a dormant `model-capabilities.json` implementation whose enabling function returns false. Writing that cache is not a working supported solution.

## Parallel subagents and workflows

Keep Agent and Workflow tools available. The default concurrent subagent limit is 20 and nesting depth is three; documented environment variables can change them. Ultracode sessions are exempt from the usual concurrent Agent-tool limit. Built-in helper models may follow family aliases, so gateway aliases for background helper models must also resolve to actual NeuralDeep routes. Subagents make their own requests and need concurrent, independent HTTP handling. [Subagents](https://code.claude.com/docs/en/sub-agents).

Dynamic workflows are available in CLI, Desktop, IDE, print mode, and Agent SDK. `disableWorkflows` and `CLAUDE_CODE_DISABLE_WORKFLOWS` disable them. `workflowSizeGuideline: "unrestricted"` removes the advisory sizing guideline, while runtime caps remain. `ultracode: true` enables standing orchestration at the session's effort level; it requires the feature/model to be available and does not manufacture availability. The literal keyword in a `-p` prompt does not opt into a workflow; invoke a workflow or enable standing orchestration explicitly. [Dynamic workflows](https://code.claude.com/docs/en/workflows).

## Desktop 3P configuration

Desktop has native third-party inference. It reads its own inference configuration rather than CLI routing from `settings.json`. The normal UI route is Help → Troubleshooting → Enable Developer Mode, then Developer → Configure Third-Party Inference; apply and restart. Gateway mode removes Anthropic-hosted cloud environments and Remote Control. SSH sessions require explicit allowed hosts and a gateway reachable from the remote machine. A loopback gateway on the desktop cannot serve a remote host without additional routing. [Gateway surface setup](https://code.claude.com/docs/en/llm-gateway-connect#desktop-app), [installation](https://claude.com/docs/third-party/claude-desktop/installation).

Native flat fields include `inferenceProvider: "gateway"`, `inferenceGatewayBaseUrl`, `inferenceGatewayAuthScheme`, and either a credential/helper configuration. `inferenceModels` entries support `name`, `labelOverride`, `supports1m`, `prefer1m`, `anthropicFamilyTier`, `isFamilyDefault`, `behavesAs`, `maxEffort`. The first is default. `behavesAs` imports a known Claude model's effort and limits; it does not expose arbitrary numeric capacities. `modelCatalogUrl` accepts only a mirror of Anthropic's signed catalog and signature; edited/re-signed catalogs are rejected. [Desktop configuration](https://claude.com/docs/third-party/claude-desktop/configuration).

Local 4.4212.0 `app.asar` read-only inspection exposed an implementation-specific storage layout: `configLibrary/_meta.json` contains `{appliedId, entries:[{id,name}]}` and `configLibrary/<id>.json` contains flat inference fields. `claude_desktop_config.json` records `deploymentMode: "3p"`. An old `enterpriseConfig` embedded there is retired. Although source mentions `CLAUDE_USER_DATA_DIR`, the packaged runtime test did not establish reliable profile isolation; the shipped launcher therefore requires explicit main-profile activation. This storage layout needs version checks and real UI validation; it is not an API contract. Linux machine policy at `/etc/claude-desktop/managed-settings.json` requires root ownership of both file and parent and rejects unknown keys.

After the user selected **main configuration**, `desktop.activate` was implemented and executed. Ordinary native Desktop startup reads its main 3P library from `~/.config/Claude-3p` on this Linux build and relocates there; it retains the previous Anthropic-auth store in `~/.config/Claude`. The activation selected the NeuralDeep library entry and persisted the 3P chooser without deleting previous preferences or history. The original ordinary app configuration was backed up under `.local/backups/desktop-20261102T151642.480282Z/`. This activation generated 85 billing/effort options at that cutoff, but did not establish that Desktop accepted or displayed them. The parent process has no `DISPLAY`, `WAYLAND_DISPLAY`, or `DBUS_SESSION_BUS_ADDRESS`, and the CUA inventory exposes no native applications. Desktop was therefore not launched or marked UI-verified. The prepared receipt preserves `ui_verified: false` and the signed-catalog, arbitrary-context and non-Claude-picker limitations.

The subsequent explicit choices were applied: the first configured entry is `nd/qwen3.8-27b@subscription`; local `/nd-design` replaces the requested design workflow, without configuring native Anthropic Design. `/nd-design` and `/nd-workflow` are installed under `~/.claude/skills` from portable `skills/` sources, with generated runtime references pointing to this checkout. The ordinary Linux `~/.local/bin/claude-desktop` launcher now refreshes the catalog, ensures the local gateway, and runs the real native binary through `desktop.launch` with `--no-proxy-server`. It preserves URI arguments. Shell syntax and persistent root bindings were checked without launching the GUI. The launcher-recovery note under `.local/backups` records the corrected test-isolation mistake and the recovered previous source honestly; no pre-edit launcher checksum is claimed.

Linux Desktop is officially beta on supported Debian/Ubuntu releases. Computer Use is unavailable on Linux; inference routing cannot enable it. Cowork requires QEMU/KVM and host permissions. [Linux Desktop](https://code.claude.com/docs/en/desktop-linux).

## Native Claude Design is a separate service

Design is documented as a Claude feature with `/design` and `/design-sync`; it includes hosted designs, sharing and synchronization. An upstream model API key does not represent that service authorization. [Claude Design guide](https://support.claude.com/en/articles/14604416-get-started-with-claude-design).

Installed 2.1.296 binary inspection confirms that native Design sends a separate first-party request to `/v1/design/mcp`, enforces an Anthropic host allowlist, and requires a design-capable claude.ai credential or dedicated interactive `/design login` authorization. A provider error explicitly excludes third-party providers. A NeuralDeep gateway cannot become that service by changing `ANTHROPIC_BASE_URL`. A local design workflow can still generate and review frontends using local tools and NeuralDeep capabilities, but must be named and described as a local alternative. Native Design integration must remain marked unverified/unavailable without its own authorization and test.

## Required evidence before broad claims

Configuration validation alone is insufficient. Verify a real tool call and tool result, streaming completion, independent parallel subagent requests, an actual dynamic workflow, manual compact, automatic compact near each relevant capacity class, model/effort switching, subscription/wallet routing, and Desktop UI state. Keep unsupported or untested cells visible. Native Anthropic-hosted services and non-Claude model behavior cannot be guaranteed by the local adapter.

## Output allowance audit after the CLI update

The CLI was subsequently updated to 2.1.316. Read-only inspection of that installed executable establishes an unknown-model default output allowance of 32000 tokens and an upper allowance of 128000. `CLAUDE_CODE_MAX_OUTPUT_TOKENS` can raise the default within that upper allowance; values above the upper allowance are clamped. Signed model runtime metadata also validates output/default-output values within 1024–128000. The older model-capabilities cache remains disabled in this build.

Consequently the configuration can request the selected provider's published output limit up to the stock client's 128000 ceiling, while the gateway enforces each actual model's own smaller published cap. A provider publishing 235929 or 943718 output tokens does not make that number a supported native client allowance. Overriding the final request through `CLAUDE_CODE_EXTRA_BODY` would require separate experiments: changing the transmitted body would not automatically update the client's output/context accounting, and a large output allowance can exceed the remaining capacity of smaller models. No such unverified bypass was added by this audit.

## Final main-profile startup evidence

After the main configuration was activated with local gateway `ANTHROPIC_API_KEY` authentication, CLI 2.1.316 completed an ordinary invocation in 22.469 seconds with exit code 0, `is_error: false`, and response `MAIN_OK`. This invocation used the actual main profile with its existing 13 plugins and 230 tools; it did not use `--settings`, `--setting-sources`, `--bare`, or a strict replacement MCP configuration. The selected upstream route was subscription `nd/qwen3.8-27b@subscription`. The bounded receipt is `.local/cli-main-profile-final-summary.json`; request-side limits and gateway binding are recorded separately by the parent validation. The CLI's result summary still reports `maxOutputTokens: 32000`, so that field alone does not establish the actual transmitted allowance.

Temporary diagnostic configurations had stalled before useful progress, including one with plugins and hooks disabled. Those cases do not establish a failure of the final main profile or identify a causal plugin. In particular, absence of `[API:request]` debug markers is insufficient evidence of no API dispatch: this marker is verbose-only and was also absent in a successful bare run. First-party OAuth/bootstrap/telemetry timeouts were present in both unsuccessful diagnostics and an earlier successful normal skill invocation. No production plugins, hooks, or optional traffic were disabled on the basis of these ambiguous diagnostics.

Native Desktop was subsequently started under a local virtual X11 display using its actual main profile. Its startup logs accepted all 117 configured model/billing/effort entries, selected the explicit subscription Qwen default, and registered all 14 NeuralDeep MCP groups. Opaque gateway model IDs satisfy the native model-name filter while labels and local routing retain the actual upstream identity. This is startup/configuration evidence, not visual picker interaction or complete Desktop feature validation. An earlier probe timed out as `not_testable`; the later namespace-isolated run under the new network policy reached `healthy`. Exact receipts, log bounds, and remaining limitations are in [VALIDATION-desktop.md](VALIDATION-desktop.md).
